# MASTER SPECIFICATION: Sector-Agnostic Swing Trading Alert Bot (Paper Trading)

## PURPOSE OF THIS DOCUMENT
This is the complete planning and design specification for a swing trading scanner and alert bot. This document defines **what** we are building, **why** we are building it this way, and **how** it should function at a system level. It does **not** contain code. It is meant to be handed to a separate build/implementation chat as the single source of truth so nothing gets lost, re-explained, or built inconsistently. Every design decision below has a reason attached to it so the builder (human or AI) understands intent, not just instructions.

This is a **paper trading system only**. No real capital is at risk. The goal is to practice, track percentage gains/losses, and refine a rules-based process over time — not to guarantee winning trades. No system, no matter how well designed, wins 100% of the time. The objective is a repeatable process with a positive expectancy across a large sample of trades, evaluated honestly through logged results.

---

## 1. THE PROBLEM WE ARE SOLVING

The previous version of this bot scanned tickers and waited for **simultaneous bullish alignment across five timeframes** — daily, 4-hour, 1-hour, 15-minute, and 5-minute — before sending any alert. This is functionally an "AND-gate": every single condition had to be true at the same time for an alert to fire.

This design has two fatal flaws:

1. **Statistical rarity.** Even if each timeframe has a moderately good chance of showing "bullish" conditions independently, requiring all five to align at once is a compounding probability problem. The more conditions you stack with AND logic, the rarer the combined event becomes — which is exactly why the bot rarely fired.
2. **Lag.** By the time five different timeframes have all turned bullish simultaneously, the move is very often already underway or already extended. The bot was catching exhaustion, not the actual opportunity.

The fix is to stop treating timeframes as a unanimous vote and instead treat them as **two separate roles**: a small number of timeframes that establish *context* (is this a healthy environment to even look at this stock?), and a single timeframe that generates the actual *trigger* (is something happening right now worth alerting on?). The trigger itself will be scored, not judged as a binary pass/fail, so we get a ranked signal instead of an all-or-nothing gate.

---

## 2. CORE PHILOSOPHY

- **Composite scoring beats unanimous alignment.** A weighted 0–100 score across multiple factors produces meaningfully more (and more useful) alerts than an AND-gate across timeframes.
- **Context and trigger are different jobs.** Context filters (daily/4H) exist to eliminate stocks that are structurally unhealthy. The trigger (15m/5m) exists to catch the actual moment worth acting on.
- **Every alert must be actionable, not just informational.** An alert without a defined entry zone, stop-loss, and target is just noise. Every single alert generated by this system must include those three things at minimum.
- **The system must track its own performance.** A trading system that doesn't log its own outcomes can't be improved. Every alert generated should eventually be tied to a logged result (win/loss, R-multiple, days held) so that the scoring weights can be reviewed and tuned based on real forward performance, not vibes.
- **Sector-agnostic.** The scanner should not favor or exclude any particular sector or industry. The scoring model is built on price action, volume, and momentum characteristics that apply universally across any liquid, tradable stock.
- **Swing timeframe only.** This is explicitly not a long-term investing tool and not a scalping/day-trading tool either. The intended holding period is roughly a single day up to a few weeks, with most trades expected to resolve within days. Nothing in this system should be optimized for multi-month or multi-year holds.

---

## 3. SYSTEM ARCHITECTURE OVERVIEW

At a high level, the system is composed of the following logical components. These are described functionally here — actual technology choices, libraries, and code structure will be determined in the build chat.

1. **Universe/Scanner Layer** — pulls in a broad, sector-agnostic list of liquid, tradable tickers (filtering out illiquid or unreasonably low-volume names) as the starting pool to evaluate.
2. **Data Layer** — retrieves multi-timeframe price and volume data (daily, 4-hour, 15-minute, 5-minute) for every ticker in the pool. This needs to refresh on a schedule aligned to the timeframes being evaluated.
3. **Context Filter Engine** — applies the daily/4H pass/fail checks described in Section 4 to narrow the universe down to a smaller "eligible" pool.
4. **Trigger Scoring Engine** — evaluates the 15m/5m trigger timeframe for every ticker still in the eligible pool and produces a composite 0–100 score per Section 5.
5. **State Tracker** — remembers each ticker's previous score so the system can detect a "fresh crossing" above the alert threshold (see Section 6) rather than repeatedly alerting on every candle a ticker stays elevated.
6. **Alert Formatter** — builds a structured alert (Section 8) containing entry zone, stop, targets, and reasoning.
7. **Discord Delivery Layer** — sends the formatted alert to a Discord channel via webhook.
8. **Exit Monitoring Engine** — for any ticker with an active/open paper position, continuously checks whether stop-loss, partial target, full target, or time-based exit conditions have been met, and sends a follow-up Discord alert when they are.
9. **Logging/Performance Layer** — records every alert and its eventual outcome (entry, exit, R-multiple, win/loss, days held) so performance can be reviewed and the scoring weights can be revisited over time.
10. **GitHub Repository** — version-controlled home for the scanner's configuration (filter thresholds, scoring weights, indicator settings), so changes to the strategy over time are tracked, reversible, and documented rather than living only inside a chat history. Trade logs and performance history can also live here as data files. This also becomes the natural place for secrets/credentials handling (API keys, webhook URLs) to be done properly via environment variables rather than hardcoded values, once we get to the build phase.

## 4. CONTEXT FILTERS (Daily + 4H) — Pass/Fail Gate

A ticker must pass **all** of the following before it's even eligible to be evaluated on the trigger timeframe. These are not scored — they are binary gates meant to eliminate structurally unhealthy or untradeable names.

- Price is above both the 20-period and 50-period EMA on the daily chart (confirms the stock is in an established uptrend, not fighting against its own trend).
- Daily ADX(14) is above 20 (confirms the stock is actually trending, rather than chopping sideways with no directional conviction).
- Relative strength versus SPY is positive over the trailing 5–10 trading days (confirms the stock is outperforming the broader market, not just drifting up with it).
- ATR% (average true range as a percentage of price) falls within a workable range — enough volatility that the stock can realistically make a meaningful multi-day move, but not so explosive that risk becomes unmanageable or unpredictable.
- Minimum liquidity threshold (average daily volume and dollar volume) sufficient that entries/exits are realistic even in a paper trading context meant to simulate real conditions.

Anything failing any one of these is dropped from consideration entirely for that scan cycle — no exceptions, no partial credit.

---

## 5. TRIGGER SCORING ENGINE (15-Minute or 5-Minute) — 0 to 100 Composite

Only tickers that passed the Context Filters are evaluated here. Each factor below contributes up to 20 points, for a maximum composite score of 100.

1. **Relative Volume Surge (0–20 pts)** — Measures current volume on the trigger candle against its recent average. A surge of roughly 1.5x to 2x or more average volume scores highly, since volume expansion is one of the most reliable confirmations that a move has real participation behind it rather than being noise.

2. **Price Structure Break (0–20 pts)** — Measures whether price is clearing a meaningful, clearly defined level: a prior resistance level, the top of a tightening consolidation range, or a well-defined base. A clean, decisive break scores higher than a marginal, barely-there break.

3. **VWAP Relationship (0–20 pts)** — Measures the stock's relationship to its intraday VWAP. Reclaiming VWAP from below after being rejected, or holding above VWAP through a shallow pullback and bouncing, both score well — these patterns tend to reflect a shift in intraday control toward buyers.

4. **Momentum Confirmation (0–20 pts)** — Measures whether momentum indicators support the move: MACD histogram turning upward, RSI crossing above the 50 midline without already being deep into overbought territory (roughly above 70), signaling room left to run rather than a move that's already exhausted.

5. **Clean Structure Above (0–20 pts)** — Measures whether there is significant overhead resistance sitting close above the current price that could immediately cap the move. A clear path with no heavy resistance nearby scores well; a stock running straight into a dense prior resistance zone scores lower even if everything else looks good.

**Score Tiers:**
- **80–100 → A-Setup:** full alert, highest conviction
- **60–79 → B-Setup:** lower-priority watchlist alert
- **Below 60 → No alert**

---

## 6. FRESH-CROSSING TRIGGER LOGIC (Critical Behavior Requirement)

The system must **not** re-alert on every scan cycle simply because a ticker's score remains above 80. This was explicitly requested and is critical to avoiding alert spam.

**Required behavior:**
- The system maintains state per ticker: its most recent composite score from the prior scan cycle.
- An alert is only generated when the score **crosses from below 80 up to 80 or above** — i.e., the previous cycle's score was under 80 and the current cycle's score is 80+.
- If the score stays at or above 80 across multiple consecutive scan cycles, no repeat alert is sent — the ticker is considered "already alerted" until its score drops back below the threshold.
- Once the score drops back below 80, the ticker is reset and becomes eligible to trigger a brand-new "fresh crossing" alert if it climbs back above 80 again later.
- This same fresh-crossing logic should apply to the B-Setup tier (60–79) independently, so a ticker isn't spammed there either.
- This state needs to persist across scan cycles (not reset every time the scanner runs), so the build chat will need to decide on a simple persistence mechanism (this can be figured out during the build phase — a lightweight file, database, or in-memory store with periodic saving all work; the point here is only that persistence is required, not which method).

---

## 7. ENTRY, STOP-LOSS, AND TARGET RULES

**Entry:**
- Triggered only on a **closed** candle (15m or 5m, whichever timeframe is used for scoring) — never mid-candle, to avoid false triggers from intra-candle noise that reverses before the close.
- Suggested entry zone: from the trigger candle's high up to a small percentage above it, giving a realistic fill range rather than a single exact price.

**Stop-Loss:**
- Whichever is tighter and still structurally sound between: (a) just below the trigger candle's low or the reclaimed structural level, or (b) 1x ATR(14) on the trigger timeframe below entry.

**Targets and Exit Management:**
- Define 1R as the distance from entry to the stop-loss.
- At 1R of profit, take a partial exit (e.g., roughly half the position) and move the stop to breakeven on the remainder — this locks in progress and removes downside risk on the trade going forward.
- Second target set at 2R or the next meaningful prior swing high, whichever is more realistic.
- For any remaining position beyond the second target, trail using a rising moving average (9 or 20 EMA) on a higher timeframe such as the 1-hour, letting winners run further when the trade is genuinely working.
- **Time-based stop:** if a position shows no meaningful follow-through within roughly 3–5 trading days, close it regardless of P/L — capital (even paper capital) sitting in a stagnant trade is an opportunity cost.
- **Hard invalidation:** if price closes back below the original stop-loss level, exit immediately and flag it clearly as a stopped-out trade in the alert and in the log.

---

## 8. DISCORD ALERT FORMAT

Every alert, whether an entry trigger or an exit event, should be structured and consistent so it's scannable at a glance. At minimum, an entry alert includes:

- Ticker symbol and setup tier (A-Setup / B-Setup)
- Composite score (out of 100) and a brief breakdown of which factors scored highest
- Suggested entry zone
- Stop-loss level
- Target 1 (1R) and Target 2 (2R)
- A one-line context summary (daily trend condition, relative strength note)

Exit alerts should clearly state which type of exit occurred (partial profit hit, full target hit, stop hit, or time-based exit) along with the resulting R-multiple and percentage gain/loss for that portion of the trade.

---

## 9. LOGGING AND PERFORMANCE TRACKING

Every single alert generated — win, loss, or still open — needs to be logged with enough detail to later calculate: win rate, average R-multiple per trade, average holding period, and overall expectancy (average R multiplied by win rate, minus average R lost multiplied by loss rate). This log is what allows the scoring weights in Section 5 to be revisited and tuned intelligently later, rather than guessed at. This log should also be structured in a way that could eventually be stored and version-controlled in the GitHub repository alongside the strategy configuration itself.

---

## 10. GITHUB AND DISCORD INTEGRATION (Planning Notes Only — Not Built Yet)

- **GitHub** will serve as the version-controlled home for: scoring weights and thresholds, context filter parameters, the trade/performance log, and any future changes to the strategy logic — so the evolution of the system over time is fully tracked and reversible.
- **Discord** remains the delivery mechanism for both entry alerts and exit alerts via webhook, exactly as in the current setup, but now carrying the richer, structured alert format described in Section 8 instead of a simple notification.
- Neither of these integrations needs to be built yet. This document exists to lock in the *design* first. Implementation (actual code, repo structure, webhook setup, credentials handling) happens in the dedicated build chat once this specification is finalized.

---

## 11. EXPLICIT NON-GOALS

- This is **not** a long-term investing tool.
- This is **not** a day-trading/scalping tool operating on sub-5-minute timeframes.
- This is **not** guaranteed to be profitable — no scoring system is. It is a structured, testable process meant to be evaluated honestly through logged paper-trading results and refined over time.
- This does **not** use real capital under any circumstance covered by this document.

---

## 12. SUCCESS METRICS

The system will be considered "working well" not by how often it fires, but by whether the logged paper-trading results over a meaningful sample size (ideally 30+ trades) show a positive expectancy — a healthy combination of win rate and average R-multiple that would, in aggregate, produce a net positive return if scaled to real capital in the future.
